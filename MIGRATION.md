# WordPress → Astro migration audit and implementation plan

Audit date: 2026-10-21

Sources used for this audit:

- Latest WordPress export: `../haibin039sblog.WordPress.2026-10-21.xml`
- Earlier comparison export: `../haibin039sblog.WordPress.2026-06-18.xml`
- Original WordPress theme: `../theme-document/`
- Current Astro site: this repository

This document separates four questions: whether WordPress data exists in the
export, whether the importer preserves it, whether Astro renders it correctly,
and whether deployment preserves the old public URLs and behavior.

The site is not yet a complete migration. It renders the main body of the
public posts, but several page types, media files, metadata fields, links, and
theme behaviors are still missing.

## 2. Navigation behavior that must be preserved

These are product requirements for the Astro version, even where the original
theme used a slightly different click target:

- Homepage left sidebar: show article titles so readers can find and open a
  post. Once pagination is added, it should show the titles on the current page
  rather than all 231 posts at once.
- Article left sidebar: show the article title followed by the real `H2`, `H3`,
  and `H4` headings from that article. Clicking a heading scrolls to it and the
  active heading follows the reading position.
- Article right sidebar: restore the same useful widgets as the homepage and
  keep the sidebar visible while scrolling on desktop, stopping before the
  footer.
- At widths of 1024 px and below: use a mobile menu and a single content column,
  following the original theme instead of compressing three columns together.

`src/components/ArticleNavigation.astro` already implements the core article
outline correctly. The remaining navigation work is pagination, mobile layout,
and the article-page right sidebar.

## 4. Data that exists but is currently discarded

The XML already contains useful data that should be preserved in frontmatter or
generated JSON:

- 229/229 public posts have exported `post_views_count`, totaling **342,467**
  per-post views in the XML snapshot. The live WordPress aggregate reported at
  migration time is **363,842**; this is the authoritative site-wide seed and
  includes activity/state newer or broader than the exported per-post sum.
- 164 posts have like metadata, totaling **530** likes.
- 147 posts have dislike metadata, totaling **18** dislikes.
- 41 public posts have a valid WordPress featured-image attachment.
- 36 posts have an older `_wp_old_slug` in addition to the exported permalink.
- 151 posts have a modification time different from their publication time.
- 10 posts belong to two categories; the current importer drops the second one.
- WordPress creators are `GB` for 210 posts and `haibin` for 19 posts; the page
  currently hardcodes `Haibin Lai`.
- 21 approved comments contain author, date, content, URL, and reply-parent data.
  The importer currently retains only per-post counts. Email and IP fields must
  never be written to public output.

The importer also removes 255 invalid XML control characters. Nine post bodies
contain 57 of those characters, mainly in technical text/code. Those nine posts
need a manual comparison with the original database or rendered WordPress page.

## 5. Media audit

The 229 imported post bodies contain:

- 2,615 `<img>` references across 164 posts
- 2,605 remote image references
- 2,574 unique remote image URLs
- 206 raw references to old-site `wp-content` URLs, representing 193 unique URLs
- 230 attachment records in WXR, but no downloaded attachment binaries

The most common image origins are the author's Tencent COS bucket, S3 bucket,
the old WordPress host, sm.ms, and jsDelivr. Only a subset of images are WXR
attachments, so downloading the WXR attachment list alone will not make the
site self-contained.

Known broken content:

- Nine `file:///C:/.../wps6.jpg` through `wps14.jpg` images in
  `人月神话-读书笔记.md`
- One `src="undefined"` image in `自顶向下了解llama-cpp-ggml.md`
- At least 21 old-site media URLs currently return a confirmed 404
- Several relative links such as `GFS`, `Yarn`, `NIC`, and `e^{-t}-1` do not
  resolve to valid static assets/routes

Required media workflow:

1. Generate a manifest containing source URL, owning post/page, media type,
   destination path, HTTP result, size, and checksum.
2. Download owned media with retries and resumable output.
3. Preserve extensions and MIME types; deduplicate by checksum.
4. Rewrite post/page HTML to the stable destination under `public/uploads/` or
   a permanent object-storage origin.
5. Produce a hard failure for `file://`, `undefined`, missing local paths, and
   unresolved old-domain media.
6. Run the checker in CI so future imports cannot silently reintroduce them.

They should not all be treated the same:

### Public content pages

they appear in the main menu. `My Friends` additionally depends on WordPress
bookmark data that is not present in WXR.

### Public interactive pages

Snake and Doom can be ported to client-side Astro pages. Their permanent
leaderboards require a separate API or can be deliberately omitted.

### Private/admin pages

Todo, Clipboard, reading statistics, and reading trend were protected by
WordPress authentication. GitHub Pages has no equivalent server-side login.
Their private records must not be copied into public JavaScript or JSON. Keep
these routes unavailable until a separately authenticated replacement exists.

`My Toys` also reads a WordPress option and can contain admin-only links. Its
configuration must be reviewed before publishing any static copy.

### Data unavailable from WXR

A WordPress database export is required to preserve any of the following:

- Friend bookmarks
- Widget placement and widget settings
- Theme options and `nicen_theme_toys`
- View-log history and trend data
- Todo items and dependency edges
- Clipboard records/files
- Snake and Doom leaderboards
- Pomodoro state

Without this database export, these features can be rebuilt, but their existing
state cannot be claimed as migrated.

## 10. Definition of complete

The migration is complete only when all of the following are true:

- Content counts are explained exactly; hand-written Astro content is not
  confused with imported WordPress content.
- Every intended public post/page has a working new URL and compatible old URL.
- Password-protected and private content is absent from the public artifact.
- Owned media is on a stable host and the build has no known broken media.
- Homepage and article sidebars follow the required title/heading behavior.
- Desktop, tablet, and mobile layouts pass visual comparison.
- Search, category/tag archives, pagination, RSS, sitemap, and 404 work.
- Historical comments and metadata are preserved according to the decisions
  above.
- Dynamic/private WordPress features are either replaced deliberately or
  documented as excluded; no missing backend state is presented as migrated.
- The final custom domain is verified after deployment before WordPress is
  retired.
