<h2>2. Overall Architecture</h2>
<p>All of the service and database, Kafka and zookeeper run in Docker. For clients, they can use port <code>8080</code> to send RESTful API. The NGINX Server will catch the requests and send them to API Service with load balance scheduling (like Round Robin). The API Service runs in Flask framework will receive and deal with the requests. They will send <code>gRPC</code> communication to DB Service and Logging Service to deal with the requests. The DB Service will communicate with PG database on port <code>5432</code>, while Logging Service will put logging message from port <code>9092</code> to Kafka, which the Administrator and know the logging information.</p>
<p><img src="https://blog-1327458544.cos.ap-guangzhou.myqcloud.com/FinalYear/20251117011447744.png" alt="image.png" /></p>
<ul>
<li>The API Service include every API described in assignment.</li>
<li>DB Service provide CRUD for products, users and orders.</li>
<li>Logging Service provide communication with Kafka.</li>
<li>RPC proto files, OpenAPI YAML file and Docker Compose File are provided.</li>
<li>NGINX and it's config is also listed in file.</li>
</ul>
<p>We also discuss some detail problems in these design:</p>
<ol>
<li>OpenAPI type of accessing API</li>
<li>Generate JWT token when login, and use JWT to check accounts and orders</li>
<li>Use string instead of float in <code>price</code> tag in OpenAPI and gRPC communication to prevent price mis-precision</li>
<li>Only store hash encrypted password in DB instead of plain password</li>
<li>Prevent SQL injection in DB Service</li>
<li>Concurrency in DB Service using <code>Transaction</code> to prevent multi-thread conflict</li>
<li>Streaming gRPC for large log data across Logging Service and API Service.</li>
</ol>

<p>Some of the CRUD example:</p>
<blockquote>
<p>We use <strong>Database Transaction</strong> to make sure <strong>concurrency</strong>. with conn: wraps everything in one transaction. If any exception is raised inside, psycopg2 will automatically ROLLBACK when leaving the block. Any concurrent CreateOrder requests targeting the same product must wait until the current transaction finishes. Two customers cannot purchase the same remaining items at the same time, the stock value read from the database is always the latest and consistent, all subsequent updates to the product row happen safely. This is the standard technique for avoiding lost updates and overselling under PostgreSQL’s default READ COMMITTED isolation level.</p>
<p>To prevent <strong>SQL injection</strong>, all database queries in the DB Service are executed using parameterized statements (e.g., <code>WHERE sid = %s</code> with <code>(request.sid,)</code> in psycopg2) instead of string concatenation. User inputs are always passed as bound parameters, so they are treated as data rather than executable SQL.</p>
<p>Use <strong>Decimal</strong> rather than float to compute the total price. And we also check the number and price that from DB.</p>
</blockquote>
<pre><code class="language-python"># ---- Orders ----
def CreateOrder(self, request, context):
    &quot;&quot;&quot;
    CreateOrder 逻辑说明（在一个事务里完成）：
      1. 使用 SELECT ... FOR UPDATE 锁定商品行，读取 price 与 stock
      2. 校验 quantity 范围（1~3）以及库存是否足够
      3. 基于数据库中的 price 计算 total_price（使用 Decimal 处理金额）
      4. 向 orders 表插入新订单记录，并返回生成的订单信息
      5. 扣减 products 表中的库存
    所有 SQL 操作都使用参数化查询（%s + 参数元组），防止 SQL 注入。
    价格只信任数据库中的 price，不信任客户端传入的任何金额字段。
    &quot;&quot;&quot;
    conn = get_connection()
    try:
        with conn:  # commit / rollback
            with conn.cursor() as cur:
                # 1. read stock &amp; price
                cur.execute(
                    &quot;&quot;&quot;
                    SELECT price, stock
                    FROM products
                    WHERE id = %s
                    FOR UPDATE
                    &quot;&quot;&quot;,
                    (request.product_id,),
                )
                prod_row = cur.fetchone()
                if prod_row is None:
                    context.abort(grpc.StatusCode.NOT_FOUND, &quot;product not found&quot;)

                price, stock = prod_row  # price: NUMERIC -&gt; Decimal, stock: int

                # 2. check quantity
                qty = int(request.quantity)
                if qty &lt;= 0 or qty &gt; 3:
                    context.abort(
                        grpc.StatusCode.INVALID_ARGUMENT,
                        &quot;quantity must be between 1 and 3&quot;,
                    )

                if stock &lt; qty:
                    context.abort(
                        grpc.StatusCode.FAILED_PRECONDITION,
                        &quot;not enough stock&quot;,
                    )

                # 3. price, Decimal
                if not isinstance(price, Decimal):
                    price = Decimal(str(price))
                total_price = price * Decimal(qty)

                # 4. insert
                cur.execute(
                    &quot;&quot;&quot;
                    INSERT INTO orders (user_id, product_id, quantity, total_price)
                    VALUES (%s, %s, %s, %s)
                    RETURNING id, user_id, product_id, quantity, total_price, created_at
                    &quot;&quot;&quot;,
                    (
                        request.user_id,
                        request.product_id,
                        qty,
                        total_price,
                    ),
                )
                order_row = cur.fetchone()
                if order_row is None:
                    context.abort(
                        grpc.StatusCode.INTERNAL,
                        &quot;failed to create order&quot;,
                    )

                # 5. minus stock
                cur.execute(
                    &quot;&quot;&quot;
                    UPDATE products
                    SET stock = stock - %s
                    WHERE id = %s
                    &quot;&quot;&quot;,
                    (qty, request.product_id),
                )
                # return
                return row_to_order(order_row)
    except Exception as e:
        conn.rollback()
    finally:
        release_connection(conn)</code></pre>

<h3>OpenAPI Server + gRPC with DB Server</h3>
<p>Take Orders_id_get as an example:</p>
<pre><code class="language-python">def orders_id_get(id_, token_info=None):
    &quot;&quot;&quot;Get a single order by id.&quot;&quot;&quot;

    order_id = id_

    stub = _get_db_stub()
    try:
        req = db_pb2.GetOrderRequest(id=order_id)
        order_msg = stub.GetOrder(req)

        return _success(&quot;Order fetched&quot;, order_to_dict(order_msg), 200)

    except grpc.RpcError as e:
        if e.code() == grpc.StatusCode.NOT_FOUND:
            logging_client.send_logs([{
                &quot;service_name&quot;: &quot;api-service/orders&quot;,
                &quot;level&quot;: &quot;WARNING&quot;,
                &quot;path&quot;: connexion.request.path,
                &quot;method&quot;: connexion.request.method,
                &quot;user_sid&quot;: &quot;&quot;,
                &quot;message&quot;: &quot;Order not found&quot;
            }])
            return _error(&quot;Order not found&quot;, 404)

        logging_client.send_logs([{
            &quot;service_name&quot;: &quot;api-service/orders&quot;,
            &quot;level&quot;: &quot;ERROR&quot;,
            &quot;path&quot;: connexion.request.path,
            &quot;method&quot;: connexion.request.method,
            &quot;user_sid&quot;: &quot;&quot;,
            &quot;message&quot;: f&quot;DB service error: {e.code().name} - {e.details()}&quot;
        }])
        return _error(
            f&quot;DB service error: {e.code().name} - {e.details()}&quot;,
            502,
        )</code></pre>
<p>This handler is a good example of how my OpenAPI-based API Service integrates JWT auth, gRPC, and centralized logging in a layered way:</p>
<ul>
<li>
<p><strong>REST + OpenAPI layer</strong>
<code>orders_id_get</code> is the controller for <code>GET /orders/{id}</code> generated from my OpenAPI spec.
The <code>id_</code> parameter comes from the path, and <code>token_info</code> is injected by the <strong>JWT bearerAuth</strong> security handler. That means:</p>
<ul>
<li>The JWT is validated <em>before</em> this function runs.</li>
<li>On success, decoded claims (e.g. <code>sid</code>, <code>user_id</code>) are available via <code>token_info</code>, even though this particular endpoint doesn’t yet enforce per-user ownership.</li>
</ul>
</li>
<li>
<p><strong>gRPC DB Service layer</strong>
Instead of talking to PostgreSQL directly, the API calls the <strong>DB Service via gRPC</strong>:</p>
<ul>
<li><code>_get_db_stub()</code> returns a gRPC stub for the DB Service.</li>
<li>The handler builds a strongly-typed <code>GetOrderRequest</code> (<code>db_pb2.GetOrderRequest(id=order_id)</code>) and calls <code>stub.GetOrder(req)</code>.</li>
<li>On success, the protobuf <code>order_msg</code> is converted into a plain dict with <code>order_to_dict(order_msg)</code> and wrapped by <code>_success(&quot;Order fetched&quot;, ..., 200)</code> as a JSON HTTP 200 response.</li>
<li>This cleanly separates HTTP/JSON concerns (API Service) from SQL/connection-pooling concerns (DB Service).</li>
</ul>
</li>
<li>
<p><strong>Error mapping and service “tiering”</strong>
gRPC status codes from the DB Service are mapped to appropriate HTTP responses at the API tier:</p>
<ul>
<li>If <code>e.code() == grpc.StatusCode.NOT_FOUND</code>, the API returns an HTTP <strong>404</strong> <code>&quot;Order not found&quot;</code>.</li>
<li>Any other gRPC error is treated as an internal backend failure and returned as HTTP <strong>502</strong> <code>&quot;DB service error: …&quot;</code>.</li>
<li>This keeps the REST interface stable while the DB tier is an internal implementation detail.</li>
</ul>
</li>
<li>
<p><strong>Centralized structured logging via Logging Service + Kafka</strong>
On every failure, the handler sends a <strong>structured log</strong> to the Logging Service client:</p>
<ul>
<li>Fields include <code>service_name</code> (<code>&quot;api-service/orders&quot;</code>), log <code>level</code> (<code>&quot;WARNING&quot;</code> or <code>&quot;ERROR&quot;</code>), HTTP <code>path</code>, <code>method</code>, and a human-readable <code>message</code>.</li>
<li>These logs are streamed via gRPC to the Logging Service, which then forwards them into Kafka, so an administrator can monitor failed <code>get-order</code> calls centrally.</li>
<li>The <code>user_sid</code> field is already reserved; once I plug in <code>token_info</code>, I can attach the authenticated user’s SID to each log entry.</li>
</ul>
</li>
</ul>
<p>Overall, this endpoint shows my backend design goals:</p>
<ul>
<li><strong>JWT-protected OpenAPI REST layer</strong> (with <code>token_info</code> plumbed in),</li>
<li><strong>A middle gRPC tier (DB Service)</strong> that encapsulates all database logic and error codes, outputing <code>status code</code> and <code>detail message</code>,</li>
<li><strong>A separate Logging Service</strong> that receives structured logs from the API Service and forwards them to Kafka for monitoring.</li>
</ul>

<h3>4.1 Which APIs require authentication?</h3>
<p><strong>No authentication required (public):</strong></p>
<ul>
<li><code>GET /</code> – Greeting API</li>
<li><code>GET /products</code> – List all products</li>
<li><code>GET /products/{id}</code> – Get product details</li>
<li><code>POST /users/register</code> – Create a new user account</li>
<li><code>POST /users/login</code> – User login, returns a JWT</li>
</ul>
<p><strong>Authentication required (JWT Bearer):</strong></p>
<ul>
<li><strong>User APIs</strong>
<ul>
<li><code>GET /users/me</code> – Get the current user’s profile</li>
<li><code>GET /users/{id}</code> – Get a specific user (only if it’s the same as the logged-in user)</li>
<li><code>PUT /users/{id}</code> – Update user info</li>
<li><code>DELETE /users/{id}</code> – Deactivate user</li>
</ul></li>
<li><strong>Order APIs</strong>
<ul>
<li><code>POST /orders</code> – Place a new order (place-order)</li>
<li><code>GET /orders/{id}</code> – Get order details (only owner can see it)</li>
<li><code>DELETE /orders/{id}</code> – Cancel an order</li>
</ul></li>
</ul>
<p>In the OpenAPI YAML, these operations are marked with a <code>security</code> section using a <code>bearerAuth</code> security scheme, so <strong>Swagger UI, connexion, etc. know they require a token</strong>.</p>

<h3>4.2 How I implement the authentication logic</h3>
<p>To create a JWT, clients first call the <code>POST /users/login</code> API with a username and password. The API Service uses gRPC to query the DB Service for the user record and verifies the password against a stored hash. On success, the API Service issues a JWT signed with a secret key loaded from the environment. The JWT payload contains the user’s <code>sid</code>, <code>user_id</code>, and an expiration timestamp.  </p>
<p>In our API service, user-specific operations such as fetching the current user profile (<code>GET /users/me</code>), updating/deactivating the current user, and creating / listing / cancelling orders are protected by JWT-based authentication.  </p>
<p>For subsequent requests, the client includes this token in the <code>Authorization: Bearer &lt;token&gt;</code> HTTP header. The API Service validates the token on each protected endpoint by verifying its signature and expiration. It then extracts the <code>sid</code> from the payload and calls the DB Service (e.g., <code>GetUserBySid</code>) to retrieve the authoritative user record and <code>user_id</code>. All downstream gRPC calls use this <code>user_id</code> instead of trusting any client-supplied identifier, so users can only access their own orders or profile. Additionally, every login and order-related request is logged via a client-side streaming gRPC connection to the Logging Service, which forwards all log messages to a Kafka topic for centralized monitoring.</p>

<h3>📌 General Selection Principles</h3>
<h4><strong>1. Use database-native types first</strong></h4>
<p>PostgreSQL has rich numeric and timestamp types, so DB types are chosen based on data characteristics.</p>
<h4><strong>2. Choose Protobuf types that safely map to DB types</strong></h4>
<p>Protobuf has fewer scalar types; for example:</p>
<ul>
<li>No decimal → use <code>string</code> or <code>int64</code> scaled representation</li>
<li>No datetime → use <code>google.protobuf.Timestamp</code></li>
</ul>
<h4><strong>3. OpenAPI must match the Proto type semantics</strong></h4>
<p>While JSON has limited primitives, it must align with Protobuf encoding.</p>

<h2>7. client-side streaming gRPC</h2>
<p>This section we will introduce and explain how the client-side streaming RPC works in our Logging Service.</p>
<p>In our implementation, the Logging Service defines a <strong>client-side streaming RPC</strong> named <code>StreamLogs</code>. The RESTful API Service acts as the gRPC client and continuously sends log messages through a single streaming RPC call, while the Logging Service receives these messages and forwards them to Kafka.</p>
<p><img src="https://blog-1327458544.cos.ap-guangzhou.myqcloud.com/FinalYear/20251120015725176.png" alt="image.png" /></p>
<p>During runtime, API Service will send StreamLogs to Logging Service, and it will publish them to Kafka. Then if no more logs, client closes stream. So by doing that we don't need to have every LogMessage with every connections since ,any log messages share a single gRPC connection.</p>
<p><img src="https://blog-1327458544.cos.ap-guangzhou.myqcloud.com/FinalYear/20251120015731917.png" alt="image.png" /></p>
<h3>1. Client Implementation (API Service)</h3>
<p>On the client side, we implement a helper function <code>send_logs(logs)</code>:</p>
<pre><code class="language-python">def send_logs(logs):
    stub = get_logging_stub()
    INSTANCE_NAME = os.getenv(&quot;INSTANCE_NAME&quot;, &quot;unknown&quot;)

    def gen():
        for log in logs:
            yield logging_pb2.LogMessage(
                service_name=INSTANCE_NAME,
                level=log.get(&quot;level&quot;, &quot;INFO&quot;),
                path=log.get(&quot;path&quot;, &quot;&quot;),
                method=log.get(&quot;method&quot;, &quot;&quot;),
                user_sid=log.get(&quot;user_sid&quot;, &quot;&quot;),
                message=log.get(&quot;message&quot;, &quot;&quot;),
                timestamp_ms=int(time.time() * 1000)
            )

    return stub.StreamLogs(gen())</code></pre>
<p>Here:</p>
<ul>
<li><code>get_logging_stub()</code> creates (and reuses) a gRPC channel and a <code>LoggingServiceStub</code> bound to <code>LOGGING_ADDR</code>.</li>
<li><code>send_logs(logs)</code> takes a list of Python dictionaries representing log entries.</li>
<li>Inside <code>send_logs</code>, we define a generator function <code>gen()</code> that:
<ul>
<li>Iterates over the input list <code>logs</code>.</li>
<li>Converts each dictionary into a <code>LogMessage</code> protobuf.</li>
<li>Uses <code>yield</code> to stream messages one by one.</li>
</ul></li>
</ul>
<p>We then call <code>stub.StreamLogs(gen())</code>. This passes the generator <code>gen()</code> as the <code>request_iterator</code> for the <code>StreamLogs</code> RPC. The RPC is <strong>client-side streaming</strong>: multiple <code>LogMessage</code> instances are sent over a single RPC call, and the server returns a <code>LogSummary</code> only after the stream is closed.</p>
<h3>2. Server Implementation (Logging Service)</h3>
<p>On the server side, we implement the <code>LoggingService</code> as follows:</p>
<pre><code class="language-python">class LoggingService(logging_pb2_grpc.LoggingServiceServicer):
    def __init__(self, publisher):
        self.publisher = publisher

    def StreamLogs(self, request_iterator, context):
        count = 0
        for req in request_iterator:
            payload = {
                &quot;service_name&quot;: req.service_name,
                &quot;level&quot;: req.level,
                &quot;path&quot;: req.path,
                &quot;method&quot;: req.method,
                &quot;user_sid&quot;: req.user_sid,
                &quot;message&quot;: req.message,
                &quot;timestamp_ms&quot;: req.timestamp_ms
            }
            try:
                self.publisher.publish(
                    topic=KAFKA_TOPIC,
                    key=req.service_name.encode(),
                    value=json.dumps(payload).encode()
                )
                count += 1
            except Exception as e:
                LOGGER.error(&quot;Publish fail: %s&quot;, e)

        LOGGER.info(&quot;Received %d logs&quot;, count)
        return logging_pb2.LogSummary(count=count)</code></pre>
<p>Key points:</p>
<ul>
<li><code>request_iterator</code> is the server-side view of the client stream. Each time the client’s generator <code>gen()</code> yields a <code>LogMessage</code>, the <code>for req in request_iterator</code> loop receives it.</li>
<li>For each <code>LogMessage</code>:
<ul>
<li>We convert it into a JSON payload.</li>
<li>We call <code>self.publisher.publish(...)</code> to send it to the Kafka topic <code>api-logs</code>, using the service name as the message key.</li>
<li>We increment <code>count</code> to track how many log entries were received in this stream.</li>
</ul></li>
<li>After the client finishes sending logs and closes the stream:
<ul>
<li>The loop terminates.</li>
<li>The server logs the total number of messages.</li>
<li>The server returns a <code>LogSummary(count=count)</code> back to the client, completing the RPC.</li>
</ul></li>
</ul>
<h3>Summary of the Streaming Behavior</h3>
<ul>
<li><strong>Single RPC, multiple messages:</strong> The API Service opens one <code>StreamLogs</code> RPC and streams multiple <code>LogMessage</code> objects through it.</li>
<li><strong>Streaming generator:</strong> On the client, a Python generator function (<code>gen()</code>) produces the log messages lazily for the gRPC stream.</li>
<li><strong>Incremental processing:</strong> On the server, <code>StreamLogs</code> processes each incoming message immediately and publishes it to Kafka.</li>
<li><strong>Final aggregation:</strong> After all log messages are sent, the server replies with a single <code>LogSummary</code>, indicating how many logs were processed for this stream.</li>
</ul>
<p>This design leverages gRPC client-side streaming to build an efficient, low-overhead logging pipeline from the API Service to Kafka via the Logging Service.</p>
<h2>7. Docker &amp; Docker Compose</h2>
<p>In my implementation, I use a single Docker Compose setup so that all containers automatically join the same user-defined bridge network and can resolve each other by service name. PostgreSQL, Kafka, the DB Service, the Logging Service, and the RESTful API Service are all declared as services in docker-compose.yml.</p>
<p>Single Docker Compose network = shared “LAN”</p>
<ul>
<li>Each service is reachable by its <strong>service name</strong> as a hostname
<ul>
<li><code>db_service</code> → gRPC DB server</li>
<li><code>logging_service</code> → gRPC logging server</li>
<li><code>kafka</code> → Kafka broker</li>
<li><code>postgres</code> → PostgreSQL</li>
<li><code>api1</code>, <code>api2</code> → RESTful API instances</li>
<li>NGINX -&gt; api1, api2</li>
</ul></li>
<li>No need to hard-code IPs; Docker provides <strong>internal DNS</strong>.</li>
</ul>
<p>Configure DB Service ↔ PostgreSQL: port 5432
Configure API Service ↔ DB Service &amp; Logging Service: port 50051 &amp; 50052
Configure Logging Service ↔ Kafka: port 9092</p>

<h2>Understanding NGINX</h2>
<p>Here I do a very simple experiment on Request. As we increased the concurrency from 50 to 400, the system was able to handle all 2000 requests successfully, and the throughput (Requests/sec) gradually increased.  </p>
<p>Beyond a concurrency of around 600, the system started dropping requests: many connections failed at the transport layer and never produced an HTTP status code, eventually falling below 30%, while the apparent Requests/sec curve peaks around 1000 concurrency, drops, and then unexpectedly rises again.
<img src="https://blog-1327458544.cos.ap-guangzhou.myqcloud.com/FinalYear/20251120013952691.png" alt="image.png" /></p>
<p>As you can see, when concurrency is 400 (that means 400 users request at one time), the success rate is 100% and dealing speed is about 800. This maybe the maximum number that system can take. After that, system can not deal with some request.</p>
<h4><strong>Why the Success rate go down as concurrency increase</strong></h4>
<p>When concurrency becomes too high for the system to handle, many requests begin failing <strong>before they even reach the application layer</strong>. This happens due to limits in the web server (NGINX), OS file descriptors, or the backend worker capacity.</p>
<p>Once these limits are exceeded:</p>
<ul>
<li>New TCP connections are <strong>rejected, reset, or timeout</strong></li>
<li>These failed requests <strong>never receive an HTTP status code</strong></li>
<li><strong>Only a subset of requests successfully passes through NGINX and reaches Flask</strong></li>
<li>Therefore, the number of successful HTTP 200 responses decreases</li>
</ul>
<p>So the success rate decreases not because the API behaves incorrectly, but because <strong>the system is overloaded and cannot accept all incoming connections</strong>, causing many requests to fail at the transport layer.</p>
<h4><strong>Why the Request speed reach limit at 1000 then drop, then rise up</strong>:</h4>
<p>This is mainly because of NGINX.</p>
<p>This behavior is a typical artifact caused by <strong>connection limits inside NGINX</strong> and how <strong>hey</strong> calculates throughput.</p>
<h5>1) <strong>NGINX has a connection limit (~1024 worker_connections)</strong></h5>
<p>Once concurrency approaches or exceeds this limit:</p>
<ul>
<li>Only a fixed number of connections are allowed to be active</li>
<li>Extra connections fail immediately without entering the queue</li>
</ul>
<h5>2) <strong>Failed connections return instantly, reducing total test duration</strong></h5>
<p><code>hey</code> computes Requests/sec as: <code>successful_requests / total_test_time</code></p>
<p>When concurrency is extremely high:</p>
<ul>
<li>Many requests fail instantly (connection refused/reset)</li>
<li>The total test duration becomes <strong>very short</strong></li>
<li>The small number of successful requests complete quickly</li>
<li>Therefore, <code>successful_requests / time</code> may appear <strong>higher again</strong>, even though the system is overloaded</li>
</ul>
<h5>3) <strong>This creates the illusion that the throughput rises again</strong></h5>
<p>In reality:</p>
<ul>
<li>The backend is <em>not</em> performing better</li>
<li>The increase is an artifact caused by:
<ul>
<li>NGINX rejecting excess connections immediately</li>
<li>hey shortening the run duration</li>
<li>Only the “lucky” in-limit connections being measured</li>
</ul></li>
</ul>
<p>So the rise after 1000 concurrency is not true performance gain, but <strong>a side effect of NGINX’s connection limit and hey’s measurement method</strong>.</p>
<p><strong>Therefore:<br />
The Requests/sec curve peaks, drops, and rises again mainly because of NGINX’s worker connection limits and how hey measures throughput.</strong></p>
<h4>Some we learn innerly: The Power of NGINX</h4>
<p><strong>This behavior actually highlights one of the advantages of using NGINX.</strong><br />
When the concurrency exceeds the server’s capacity, NGINX intentionally rejects excessive connections immediately. This “fail-fast” behavior prevents resource exhaustion, protects backend services, and ensures that the valid in-limit connections can still be processed quickly.</p>
<p>In other words, instead of letting the entire system become slow or crash, NGINX performs graceful degradation:<br />
it sacrifices excess traffic to preserve the performance and stability of the remaining requests.</p>
